# База данных «Топаз АЗС»: что известно

Изучена копия рабочей базы одной АЗС (2026-10-31): `ProgConfig.Version = 3.15.20.12096`, Firebird **2.5.9**, ODS 11.2, кодировка UTF8, страница 8 КБ.
Сам файл базы в репозиторий **не попадает** (`*.fdb` в `.gitignore`): в нём реальные данные АЗС.

## Общие особенности

- **117 пользовательских таблиц**, 23 процедуры, 112 генераторов, около 400 триггеров.
- Имена в **смешанном регистре в кавычках**: `"flOrders"`, `"SessionID"`. Без кавычек запрос не сработает.
- Префиксы: `dc*` — справочники, `fl*` — топливо, `tr*` — товарные документы, `rg*` — регистры (движения), `cm*` — касса, `sys*` — системные таблицы и журнал.
- Домены: `TID` = INTEGER (ключи), `TCurrency`/`TVolume` = NUMERIC(15,2), `TQuantity` = NUMERIC(15,3), `TDensity` = NUMERIC(15,4), `TBoolean` = INTEGER 0/1, `TDateTime` = TIMESTAMP (**местное время без пояса**), `TXmlBlob` = BLOB TEXT.
- В транзакционных таблицах **нет даты изменения**. `modifyDate` есть только у части справочников, и это служебное поле синхронизации с офисом.
- Строки меняются после вставки: заказ `flOrders` создаётся при старте налива и обновляется по окончании.
- ID в `flOrders` и `sysEvents` растут вместе со временем (проверено на всех строках).
- Триггеры Топаза вызывают UDF (`MD5`), поэтому вставка или изменение через сторонний клиент без библиотек Топаза падает. Агенту это не мешает: он только читает.
- Строк, которые ссылаются на несуществующую смену, нет (проверено для `flOrders`, `rgCashes`, `rgFuels`, `trFastTradeH`).

## Что выгружается

Полный список — `src/Topaz.Agent/datasets.json` (105 таблиц). Его можно править без пересборки агента: таблица, которой нет в другой версии Топаза, пропускается с предупреждением в логе.

**Не выгружаются:** служебные таблицы синхронизации и журналы изменений (`sysDataChangeLogs`, `sysDataChangeLogTables`, `sysDataChangeTypes`, `syncData`, `syncGlobalErrors`, `sysExportExceptions`), служебные (`sysModules`, `sysConsts`, `sysDescriptions`, `sysUsersLaw`), таблицы без PK (`rgDCWebOfficeTransaction`, `rgOEMediaTransaction`).

**Исключённые колонки:** `dcAgents.Password`, `sysUsers.PswHash`, `sysUsers.Psw`, `sysUsers.SecurityData`, `dcPaymentModes.Config`, `ipRemitPackets.Packet` (пакет обмена с офисом — BLOB до сотен КБ на строку; на GoodOil Кетченеры 54 тыс. строк, 131 МБ; 32-битный агент на АЗС «Дизель» с базой 1 ГБ падал с OutOfMemory, читая его целиком). Любой BLOB больше `Collection:MaxBlobBytes` (64 КБ) агент отправляет как `null`.

## Сверка с отчётами Топаза (2026-10-31)

Сверка шла с двумя XML-экспортами из самого Топаза той же АЗС: экспорт данных за октябрь и агрегированный экспорт смены 80. Источником для сравнения служила центральная БД, загруженная агентом, то есть проверялась вся цепочка «Топаз → агент → сервер». Скрипты лежат в `tools/reconcile/`.

| Проверка | Результат |
|---|---|
| Экспорт за период (`DataPacket`): 33 таблицы, 1043 строки, около 30 тыс. значений | 1043/1043 строки совпали поле в поле |
| Экспорт смены 80, пересчёт каждого раздела из строк | 1083 проверки, 0 расхождений |
| Экспорт смены 80 из SQL-представлений центра (`v_shift_*`, `item_rests_at`) | 108 проверок, 0 расхождений |

Чувствительность скрипта проверена: подмена одного значения на 1 копейку обнаруживается.

### Откуда берутся цифры отчёта смены

| Раздел отчёта | Источник в БД | Правило |
|---|---|---|
| `Session` | `sysSessions` | `SessionNum`, время начала и конца, `UserName` |
| `Tanks` | `flSesTanks` (+ `dcTanks.DeadRest`, `DeadRestLiter`) | все резервуары смены, даже без отпуска. `EndFact*` пусты, если замеры при закрытии не вводились (`FactFuelVolume IS NULL`) |
| `Hoses` | `flSesHoses` | `HoseNum` = `ThroughNumber`, `StartCounter`/`EndCounter` = `StartAdder`/`EndAdder`. Разница счётчиков = сумма `flOrders.Volume` = `flSesTanks.PumpVolume` (2080,25 л) |
| `OutcomesByRetail` | `flOrders` | группировка по резервуару, рукаву, топливу, **названию** вида оплаты, `Remark`, агенту и карте. `OrderCount` включает заказы с нулевым объёмом (прерванный налив). `OrigPrice` = `Price` — по описанию формата это базовая цена («цена стелы») до скидки; в смене 80 скидок по цене не было, поэтому она совпала с ценой колонки |
| `OutcomesByRetailDetail` | `flOrders` | одна строка на заказ, все поля 1:1 |
| `ItemOutcomesByRetail` | `trFastTradeH` + `trFastTradeD` | группировка по товару, виду оплаты, контрагенту и `IsReturn`; `Amount` = Σ `Total`, `PriceFastTrade` = `Price` |
| `ItemOutcomesByPaysheet` | то же | **`Price` здесь — это Σ цен строк, а не цена** (11 шт × 150 → `Price=900` при 6 строках). Использовать нельзя |
| `CashFlow` | `rgCashes` | Σ `Amount` по `DocTypeID` и `CashID`; `Remark` берётся из `cmCashReceipt`/`cmCashOut`. В сумме за смену получилось 0: всё выдано |
| `TradeDocsOutActs` | `trOutActH`/`D` | акты с `DateDoc` внутри смены |
| `ItemRests` | Σ `rgItemRests.Quantity` с `Date ≤ EndDateTime` смены | **остаток на момент закрытия смены**, а не на момент экспорта (34/34 против 27/34) |

### Что выяснилось о данных

- **Уровнемеры (проверено 01.11.2026).** `dcTanks.LevelGauge` — GUID драйвера уровнемера (на «Цаган Аман» у резервуаров 1–3), `IsNonDimensional` — признак безразмерной ёмкости. При закрытии смены Топаз пишет замер в `flSesTanks` (`FactFuelVolume`, `Height`, `Density`, `Temperature`) и `LossVolume`/`SurplusVolume` = расхождение с учётом; следующая смена начинается с замера (`StartFuelVolume` = прошлый `FactFuelVolume`). Текущих показаний между сменами в выгружаемых таблицах нет (`flTankLevelEvents` пуста). Неоформленный слив виден как огромный `SurplusVolume` (смена 1337: +8 168 и +17 634 л без `flRecepts`).
- **Ёмкости хранения и перемещения (проверено 11.11.2026).** Документа «перемещение топлива между резервуарами» в Топазе АЗС нет: в `rgFuels` встречаются только `DocTypeID` 6 (отпуск), 7 (приём), 11 (тех. возврат), 12/13 (излишки/потери). В Кетченерах есть ёмкость хранения СУГ 45 м³, в Топаз не заведённая: весь слив газовоза (~18 900 л) оформляют приходом в рабочую ёмкость СУГ (TankID 236, 20 000 л), поэтому её учётный остаток — это рабочая ёмкость и хранение вместе и часто больше вместимости (190 из 262 смен с приходом, максимум 31 649 л). Сценарии учёта — в `docs/storage-tanks.md`.
- **Пометка «Б» есть не на всех АЗС (проверено 01.11.2026).** На GoodOil и «Цаган Аман» оплата картой («Банковская Карта», «Банк. Терминал») и по ведомостям («ВЕДОМОСТИ») записана с `AmountCash > 0` без «Б», но в кассу (`rgCashes`, `DocTypeID = 6`) не проводится ни разу, а наличные проводятся всегда. У `dcPaymentModes` нет поля типа (только `Name`, `PMID`, `Color`, `ExtCode`, `InstID`), поэтому центр определяет способ оплаты по названию вида оплаты (см. `docs/web.md`, «Способы оплаты»). Отпуски по «Е1КАРД» (топливная карта) у GoodOil записаны с `Amount = 0`.
- **Наличные или безнал определяются не по виду оплаты.** Признак безнала — `flOrders.Remark = 'Б'` вместе с `AmountCashless > 0`. Заказ с видом оплаты «Терминал Альфабанк» без «Б» проведён как наличные: он попал в `rgCashes` на кассу «ФР Штрих-М». В центре для этого есть вычисляемое поле `fuel_sales.payment_kind` (`cash` / `cashless` / `mixed` / `none`).
- **`AmountCash`/`AmountCashless` — это предоплата до скидки, а `Amount` — итоговая стоимость.** Пример: залив на 1500 ₽ по 48 ₽ со скидкой 1 ₽/л даёт `AmountCash=1500`, `Amount=1499,77`, `AmountDiscount=31,91`. Выручку считать по `Amount`. Касса (`rgCashes`) тоже ведётся по `Amount`.
- **Одно название вида оплаты бывает у нескольких ID**: «НАЛИЧКА» = 109 и 115, «СКИДКА» = 110, 112 и 113. Отчёты Топаза группируют по названию. `ExtCode` у видов оплаты пустой, так что сопоставление с 1С придётся настраивать в центре.
- `PMID` у вида оплаты — GUID платёжного модуля (драйвера), а не идентификатор вида.
- «Тех. прокачка» и «Переливы» имеют `Amount = 0`, но входят в отпуск из резервуара и в счётчики ТРК.
- Около 10% заказов с `Volume = 0` (152 из 1555) — прерванные наливы. Топаз считает их в `OrderCount`.
- `StatusOrder = 0`, `OrderSource = -1`, `CardType = -1` у всех 1555 заказов: на этой АЗС карты и внешние источники заказов не используются, смысл значений по этим данным не установить.
- **Экспорт за период режет по времени операции, а не по сменам.** Из смены 60 (30.09–01.10) в экспорт за октябрь попали только 13 из 32 отпусков, те, что после 01.10 00:00. Справочники экспортируются только в использованной части (1 резервуар из 5). Чтобы центральные отчёты «за период» совпадали с Топазом, фильтровать надо по `sold_at`/`doc_at`, а не по сменам.
- **Печатный «Отчёт за период» в Топаз-АЗС устроен иначе, чем экспорт** (вики Топаза, pageId 1179976). Он берёт смены, начатые в периоде, целиком; смена, начатая до «От», не попадает совсем. Проверено 03.11.2026 на той же выгрузке: у смены 60 на проде 32 отпуска, 19 из них 30.09, в экспорт за октябрь они не попали. Значит, экспорт режет по времени, а печатный отчёт — по сменам. Сервис считает по времени операций. С печатным отчётом цифры совпадут, если «От»/«До» поставить ровно на начало первой и конец последней смены.
- **Вид оплаты у налива можно поменять задним числом** (Отчёты → Журнал заказов отгрузочных постов, при закрытой смене). `flOrders.PaymentModeID` старой смены меняется; агент присылает это как обычное изменение строки.
- **Переливы** (вид оплаты «Переливы», `PaymentModeID = 0`): расхождение аппаратных счётчиков рукава с программными. `Amount = 0`, `Volume` бывает отрицательным (программа записала налив, которого не было). Без регистрации перелива смену не закрыть. Частые переливы на одном рукаве — правило `hose_overflows`.
- **Свёртка базы** (`TopazAZSDataUtility.exe`, «Свёртка документов» до выбранной смены) удаляет документы старых смен, оставляя остатки. Агент видит это как удаление строк. Центр не применяет удаления строк смен, закрытых больше `Topaz__HoldDeletesAfterDays` (3) дней назад: они копятся в `held_deletes`, правило `history_deleted` сообщает об этом. Как именно свёртка меняет таблицы, на реальной базе пока не проверено.
- Ошибка в справочнике: у «Кофе МАЛЫЙ» `dcItems.FullName = 'Кофе БОЛЬШОЙ'`. Отчёты показывают это как есть.
- Огромный остаток «Кофе МАЛЫЙ» (999 906) — по-видимому, условный бесконечный остаток для товара собственного производства.
- **Безопасность:** собственный экспорт Топаза за период содержит `sysUsers.PswHash` и `Psw`. Передавать такие файлы наружу нельзя. Агент эти колонки не выгружает.

## Описание XML-выгрузки Топаза (DataPaket 3.15)

Официальный документ «Описание XML-выгрузки» (wiki Топаза, раздел загрузок) описывает агрегированную выгрузку по сменам — тот формат, что лежит в `samples/экспорт смена.xml`. Копия документа — `samples/Описание XML-выгрузки.docx` (папка не попадает в git). Как разделы выгрузки собираются из таблиц, сверено выше, в «Откуда берутся цифры отчёта смены»; здесь — то, что добавляет само описание. Цифры по данным центра проверены 01.11.2026.

**Формат:** корень `DataPaket` (`Version="3.15"`, `DateTime`, `Type="Aggregated"`, `AZSCode`) → `Sessions` → `Session` (`SessionNum`, `StartDateTime`, `EndDateTime`, `UserName`) → разделы смены. Типы данных:
- `Float` — десятичная дробь с запятой, до 3 знаков после неё;
- `DateTime` — `DD.MM.YYYY hh:mm:ss` (24 часа), `Date` — `DD.MM.YYYY`, `Time` — `hh:mm:ss`;
- `Boolean` — `"0"` / `"1"`;
- пустые элементы могут отсутствовать;
- Топаз обещает расширять формат, сохраняя описанные элементы и атрибуты.

| Раздел | Что это | Что важно для центра |
|---|---|---|
| `Tanks` / `Tank` | остатки по резервуарам на смену (`StartFuelVolume`, `EndFact*`, `DeadRest`, `DeadRestLiter`) | соответствует `flSesTanks` |
| `Hoses` / `Hose` | счётчики рукавов (`StartCounter`, `EndCounter`, `PumpNum`, `NumInPump`, `HoseType`) | соответствует `flSesHoses`; счётчик переходит через 999 999,99 → 0 (учтено в проверках с 1.6.1) |
| `OutcomesByRetail` | реализация через ТРК, свёрнутая по резервуару, рукаву, ГСМ, виду оплаты | **`OrigPrice` — базовая цена (цена стелы) до скидки.** **`Remark` — метка правила обслуживания внутри одного вида оплаты, например номер порога многопороговой скидки**, а не только пометка безнала «Б» |
| `OutcomesByRetailDetail` | то же по каждому заказу (`OrderNum`, `OrigPrice` — «базовая цена», `ExtData` — XML с доп. характеристиками) | `flOrders` 1:1 |
| `OutcomesByWholesale`, `IncomesByWholesale` | отпуск и приход через АСН («Топаз-Нефтебаза») | **`AccountingType`: 0 — на литры, 1 — по массе (кг).** Учёт по массе описан только здесь; розничные сливы АЗС идут в литрах |
| `IncomesByDischarge` | поступление топлива сливом (`DateTime`, `DocNumber`, `TankNum`, `Density`, `Mass`, `Volume`, `Discrepancy`, `Price`, `PartnerName`) | `flRecepts`. **`Price` — цена товара по накладной** (`flRecepts.DocFuelPrice`): на проде пусто во всех 327 сливах, поэтому цену сливов вводят в центре («Себестоимость»). Масса и плотность на проде недостоверны (масса = литрам, плотность = 1400); литры (`DocVolume`) совпадают с движением `rgFuels` во всех сливах |
| `ItemOutcomesByRetail` | реализация товаров по товару и виду оплаты | **`PriceIn` — приходная цена** по категории цены из константы (0, если категория не задана), `PriceRetail` — расходная, `Nds` — ставка, `FRDepartment` — секция ФР |
| `ItemOutcomesByPaysheet` | реализация товаров по контрагентам | `Price` — сумма цен строк, не цена (см. выше) |
| `CashFlow` | движение денег по типу документа и кассе | `rgCashes` |
| `OutcomesByCoupon` | талоны пооперационно (`CouponCode`, номинал `CouponVolume`, фактически использовано `VolumeFact`) | вероятно `rgCoupons` (не сверялось: на наших АЗС талонов нет); в центре не показывается |
| `OutcomesByOffice` | реализация через расчётный и дисконтный центр (`CardCode`, `Schema Type`: 0 — дисконтный, 1 — расчётный центр, `PartnerINN`, `AmountExtCode` — кошелёк) | в центре не показывается |
| `HosesLocking` | установка и снятие блокировки рукавов (`Action` 0 / 1, `Description` — причина, пользователь) | вероятно `flLockHoses` (не сверялось); в центре не показывается |
| `TechReturns`, `SurplusPostings`, `LossRetirements` | тех. возвраты в резервуар, оприходование излишков, списание потерь | `flTechReturns`, `flSurplusPosting`, `flLossRetirement`; агент их выгружает, отдельных отчётов нет |
| `TradeDocsInBills` | приходные накладные на товары (`PriceName`, контрагент, склад, фирма; строки: `Quantity`, `Price`, `Amount`, `NdsAmount`, `Total`, `NdsName`) | `trInBillH` / `trInBillD` (`WithinNDS` — цена с НДС). На проде: GoodOil — 370 накладных, 3 171 строка, цена есть у 96 %, покрывают 461 товар при 450 проданных, последняя от 08.02.2026; «АЗС Старт» — 5 накладных за сентябрь–октябрь 2026. См. «Открытые вопросы» |
| `TradeDocsOutBills`, `TradeDocsInActs`, `TradeDocsOutActs`, `TradeDocsMoveItems` | расходные накладные, акты оприходования и списания, перемещения | `trOutBillH`/`D`, `trInActH`/`D`, `trOutActH`/`D`, `trMoveItemH`/`D` |
| `ItemRests` | остатки товаров по складам | на момент закрытия смены (см. выше) |

## Открытые вопросы

- Смысл `StatusOrder`, `OrderSource`, `CardType`: нужна АЗС, где работают топливные карты или ведомости.
- **Себестоимость товаров из приходных накладных Топаза** (`trInBillD.Price`, с НДС или без по `trInBillH.WithinNDS`). Сейчас цены товаров вводятся в центре вручную. У GoodOil накладные есть до февраля 2026, у «АЗС Старт» — единичные. Брать ли их автоматически (и что делать с периодом, когда накладные не вносились), решает владелец.
- Как `rgCashes` проводит смешанную оплату (наличные + безнал в одном заказе): в изученных данных таких заказов нет.
- Нужен ли `CardCode` (номер топливной карты) в центре в открытом виде. Сейчас он передаётся по TLS как есть и в логи не пишется.
- Можно ли открыть доступ к Firebird АЗС по сети (сейчас агент ставится на тот же ПК и ходит на `127.0.0.1:3050`).
